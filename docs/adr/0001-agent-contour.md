# Агентный контур: узкие агенты под оркестратором, действия через карточку, права в коде и политиках

## Контекст

Чат в панели облачного хостинга. Владелец аккаунта спрашивает, за что списаны деньги, какая у
сервера конфигурация и что будет при переходе на другую. Еще он просит сменить конфигурацию,
подключить бэкапы или поменять почту для уведомлений об авариях.

Ответ и действие стоят по-разному. Неверный ответ обходится повторным вопросом. Неверная смена
конфигурации перезагружает рабочий сервер, меняет счет и может упереться в правило, которое не
откатить (диск не уменьшается).

Обязательные ограничения:

- действие не исполняется без явного «да» владельца по карточке с ценой «до» и «после»;
- повтор «да», запроса или вызова не исполняет действие второй раз;
- права решает код: разработчик команды только читает, инженер поддержки видит обзор и ничего не
  меняет, чужой аккаунт недоступен ни при какой формулировке;
- каждый исход, включая отказы, восстанавливается по журналу;
- инструкция в чате или в статье базы знаний не доводит до исполнения;
- отказ проверки текста закрывает действия и оставляет чтение;
- по умолчанию работает локальная модель.

## Решение

- Оркестратор пишем кодом на Python, агенты – OpenAI Agents SDK. Ход: планировщик возвращает план
  данными (`Plan`), код пропускает его через гейт, узкие агенты исполняют шаги, редактор пишет
  ответ по их докладам.
- Агенты узкие: данные аккаунта, база знаний, конфигурация, эскалация. Набор инструментов задается
  при сборке агента, это первый allowlist.
- Системы хостинга подключаем MCP-серверами по streamable HTTP: чтение (`account`, `billing`, `kb`)
  и отдельный action-MCP для действий. Токен JWT RS256 выпускается на каждый сервер отдельно
  (аудитория равна адресу сервера), субъект берется только из токена.
- Действие делится на `prepare_*` для модели и `execute_action` для кода. Карточка подтверждения –
  конечный автомат с TTL, «да» распознает код. Ключ идемпотентности знают оркестратор и биллинг.
- Права: барьер 1 при сборке агентов, барьер 2 перед вызовом, проверка токена на сервере.
  Подтверждение и лимит сессии – политики Dogwood в отдельном PDP, при его отказе действия закрыты.
- Guardrail – отдельный сервис без состояния, проверяет текст до модели и после нее. Его вердикт
  только флаг для политики.
- Все состояние (моки, карточки, ключи, журналы, векторы базы знаний) – в одном Postgres с pgvector.
- Деньги храним и считаем целыми копейками.

## Альтернативы

Один агент со всеми инструментами; LangGraph; инструменты функциями в процессе без MCP; один токен
на все серверы; права и подтверждение в промпте; OPA/Rego вместо Cedar/Dogwood; guardrail
библиотекой внутри оркестратора; отдельная векторная база.

## Почему

- Один агент со всеми инструментами путает домены, а права у него общие на все случаи.
- LangGraph дает граф, а у нас линейный ход: план → гейт → агенты → редактор.
- Без MCP системы хостинга доверяли бы оркестратору, а владелец данных должен проверять сам.
- Один токен на все: кража одного открывает весь контур, спецификация MCP это запрещает.
- Запрет в промпте непредсказуем, не проверяется тестом и уступает переубеждению.
- Rego не умеет условий по истории, а «да после подготовки той же карточки» и «не больше двух
  смен за сессию» – как раз они.
- Guardrail в оркестраторе нельзя ни масштабировать, ни уронить отдельно, а падение фильтра –
  сценарий, который мы обязаны проверять.
- Отдельная векторная база – лишний сервис при десятке статей.

## Компромиссы

Пять процессов вместо одного; задержка на планировщик и редактор; Dogwood молодой (август 2026),
живые события в `dogwood-py` без меток времени, окна `formerly` проверяем replay-тестами;
guardrail на правилах годится для стенда, не для продакшена.

## Когда пересматривать

- Ход стал графом с возвратами (агент ждет другого агента) – смотрим на LangGraph.
- Малая модель с дообучением закрывает маршрутизацию на замере – планировщик только для сложных
  обращений.
- Действий больше десятка и у них разные владельцы – политики по доменам, PDP на каждый.
- Счетчик сессии обходят новой сессией – лимит переносим целиком на сторону биллинга.
